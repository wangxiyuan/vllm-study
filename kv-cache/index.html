Chapter 00

KV Cache 全景

四个模型、四种 spec、七个环节

代码基线：vllm-project/vllm @ 4e964b2623（2026-10-17）。

0. 为什么 KV cache 是核心

自回归生成时，每个新 token 都要和历史上所有 token 做 attention。历史 token 的 K/V 不会变，所以缓存它们，decode 每步只算新 token 的 K/V，再读缓存。这个缓存就是 KV cache。

它同时决定三件事：

  • 显存容量：能同时服务多少条请求、多长上下文；
  • 带宽：decode 每步要搬多少字节，直接决定 token/s；
  • 调度：块怎么分、前缀怎么复用、谁被抢占。

这四个模型没有一个是“纯 full attention”：

模型 参数量（总/激活） 结构 KV cache 的本质
DeepSeek-V4.1-Flash 552B / 8B 输入、16B 输出 40 层 sparse MLA；跨层共享 compressed KV 每层一份 SWA（窗口 128）+ 4 个 source 层的 compressed KV + 8 个 indexer KV + compressor state
Kimi K3 2.8T / 104B 93 层：24 层 MLA + 69 层 KDA 24 份 MLA KV（576 维/头）+ 69 份固定大小的 KDA recurrent state
Qwen3.8-Flash-Next ≈180B（125B 主干 + 51B n-gram + 4B MTP）/ 6B 48 层：12 层 full attention + 36 层 GDN 12 份 GQA KV（2 KV heads × 256）+ 12 份 QSA 压缩 key/ring + 36 份 GDN state
GLM-5.3-Flash 320B / 18B 45 层：11 层 sparse MLA + 34 层 KDA 11 份 MLA KV（512 维）+ 11 份 indexer kpool cache + tail ring + 34 份 KDA state

因此必须同时掌握四种 KVCacheSpec：

  • MLAAttentionSpec / SlidingWindowMLASpec：按 token 线性增长的 paged KV；
  • FullAttentionSpec：Qwen 的 GQA 主 KV；
  • MambaSpec：不随序列长度增长的 recurrent state（KDA/GDN）；
  • CircularBufferSpec：每请求固定一个 ring block（compressor/indexer tail/QSA ring）。

1. 四个模型的关键差异

  1. DeepSeek V4.1 的 KV 不在每一层都存一份。
    kv_source_layer_ids=[2,8,14,20]，只有这 4 层拥有 compressed KV；其余层通过 compressed_cache_prefix 读 source 的 cache。每层另有自己的 SWA cache（窗口 128）。这是“跨层 KV 共享 + 分层压缩”，和传统 MLA 完全不同。
  2. Kimi K3 的 69 层 KDA 不是 attention。
    它们没有 paged KV，只有固定大小的 conv state + recurrent state（MambaSpec）。序列从 8k 到 1M，这 69 层的 cache 大小不变。
  3. Qwen3.8 的 full attention 是 GQA，不是 MLA。
    12 层 full attention：num_kv_heads=2, head_dim=256；另外有 QSA 的压缩 key cache（tokens_per_state=4）和 ring（CircularBufferSpec），以及 36 层 GDN state。
  4. GLM-5.3 的 sparse attention 是“无 RoPE 的 MLA”。
    qk_rope_head_dim=0、kv_lora_rank=512、qk_nope_head_dim=256；每层 512 维 latent。indexer 用 tokens_per_state=index_kpool=4，tail 用一个 CircularBufferSpec 保存未满 pool 的 raw K。

2. vLLM 的七个环节

  1. 层声明 spec：每个 attention/cache 层实现 get_kv_cache_spec()，返回自己的 KVCacheSpec 或 None。None 表示这层不拥有 KV（共享 source 或 encoder-only），不代表没有 cache。
  2. worker 收集：GPUWorker.get_kv_cache_spec() 遍历所有 AttentionLayerBase，跳过 KV-sharing 层，并用 backend 的 customize_attention_spec() 修正布局。
  3. core 分组：get_kv_cache_groups() 把 layer spec 合并成 KVCacheGroupSpec。所有层可 merge → 1 组；同类型 → UniformTypeKVCacheSpecs；混合类型 → 按 spec/page size 拆组。
  4. 算显存与布局：get_kv_cache_config_from_groups() 算 bytes_per_block、num_blocks，并为每个 group 生成 KVCacheTensor 的 offset/layer_stride/block_stride。
  5. 建 tensor：allocate_kv_cache() 分配一块 int8 backing，create_kv_cache_views() 用 as_strided 生成 [L, B, H, N, C] 逻辑视图，再拆成每层 4D [B, H, N, C]。
  6. 绑定到层：bind_kv_cache_to_layers() 调每层的 bind_kv_cache()；MLA squeeze 掉 head 维，Mamba 拆成 conv/recurrent view。
  7. 运行时寻址：BlockTables.compute_slot_mappings() 为每个 token 算 slot；attention metadata builder 按 group 生成 block table、seq_lens、slot_mapping。

3. 关键对象

对象 作用
KVCacheSpec 一层 cache 的“类型 + 形状 + 生命周期”声明
AttentionSpec paged attention 的通用字段（heads/head_size/dtype/tokens_per_state）
MLAAttentionSpec MLA latent cache（head_size_v=0，通常 1 个 KV head）
SlidingWindowMLASpec 带窗口的 MLA cache
MambaSpec KDA/GDN 的固定 state（conv + recurrent）
CircularBufferSpec 每请求 1 个 ring block，不参与前缀缓存
KVCacheGroupSpec 共享同一 block table 的一组层
KVCacheConfig num_blocks + 每个 group + 每个 tensor 的布局
KVCacheTensor 一段 backing allocation 的 offset/layer_stride/block_stride
BlockPool / KVCacheBlock 物理 block / ref_cnt / LRU

4. 主链路

get_kv_cache_spec()                         # 每层声明
  → GPUWorker.get_kv_cache_spec()           # 收集 AttentionLayerBase
  → get_kv_cache_groups()                   # 按 spec/page size 分组
  → get_kv_cache_config_from_groups()       # bytes_per_block, num_blocks, tensors
  → allocate_kv_cache()                     # int8 backing + as_strided
  → bind_kv_cache_to_layers()               # 每层 4D view
  → BlockTables.compute_slot_mappings()     # 运行时 slot

5. 三个关键入口

  • 先看 get_kv_cache_spec()：它决定这层有没有 cache、cache 长什么样、是否共享。
  • 再看 group：group 决定 block table 和分配粒度；同 group 共享 block id，不共享 KV 内容。
  • 最后看 slot_mapping：它把“逻辑位置”变成“物理 slot”，是运行时读写 cache 的桥。

0.1 “多少 B”到底指什么

  • B = billion（十亿），T = trillion（万亿）；2.8T = 2800B。
  • 总参数：权重文件里一共有多少参数（MoE 的所有专家都算）。
  • 激活参数：每个 token 实际参与计算的参数（MoE 只激活 top-k 专家）。
  • DeepSeek V4.1 是非对称结构：输入激活 8B、输出激活 16B，总参数 552B。
  • Qwen3.8 的 125B 是主干；51B n-gram embedding 和 4B MTP 是额外参数，合计约 180B，但每个 token 只激活 6B 主干。
  • KV cache 大小不由总参数决定：GLM 320B 的 KV 比 Kimi 2.8T 小，因为 GLM 只有 11 层 sparse MLA、Kimi 有 24 层 MLA；Qwen 180B 的 GQA KV 又比 GLM 大，因为每层 2 个 KV 头 × 256 维。

最重要的一句话：

  • DeepSeek V4.1 的 KV cache 是“每层 SWA + 少数 source 层 compressed KV + indexer/compressor”，消费者层不拥有 compressed cache；
  • Kimi / Qwen / GLM 是“少量 attention 层 paged KV + 大量线性注意力层固定 state”。

1.1 结构

  → kv_a_proj (512 + 64) → compressor (ratio 0/1/2)
  → sparse MLA (64 heads, head_dim 512, rope 64)
  → o_lora 1024 / o_groups 8
  → MoE (384 routed + 1 shared, top-6)

关键 config：

compress_ratios 的长度是 43：40 个 backbone + 3 个 MTP。backbone 的分布：

层号 ratio 含义 是否有 compressed KV
0–1 0 纯 SWA 否

20–39 1 1 个 token 1 个 state 仅 source 层 20
40–42 0 MTP 否

1.2 每层到底有哪些 cache

这是 V4.1 最容易被误读的地方。get_kv_cache_spec() 在 vllm/models/deepseek_v41/attention.py:1195：

if not self.is_kv_source:
    return None
...
return MLAAttentionSpec(
    block_size=...,
    num_kv_heads=1,
    head_size=self.head_dim,          # 512
    tokens_per_state=self.compress_ratio,  # 1 or 2
    cache_dtype_str=self.kv_cache_dtype,
    model_version="deepseek_v4",
    state_content_bytes=...           # fp8_ds_mla: 584
)

但每层另有一个独立注册的 SWA cache 模块，在 attention.py:566：

self.swa_cache_layer = DeepseekV4SWACache(
    head_dim=self.head_dim,           # 512
    window_size=self.window_size,     # 128
    dtype=...,
    block_size=32,
    packed_bytes_per_token=self.swa_bytes_per_token,  # 584
    ...
)

所以对一层来说：

层类型 拥有的 cache spec 类 关键字段
所有层 SWA cache（窗口 128） SlidingWindowMLASpec window=128, block=32, head=512, tokens_per_state=1
source 层 2/8/14/20 compressed KV MLAAttentionSpec head=512, tokens_per_state=2（2/8/14）或 1（20）
source 层 2/8/14/20 compressor state CircularBufferSpec head=512?, 1 block/req
index source 层 2/8/14/20/24/28/32/36 indexer KV MLAAttentionSpec head=128, tokens_per_state=2/1
其他层 无 compressed KV 返回 None 通过 compressed_cache_prefix 读 source

get_kv_cache_spec() 返回 None 不代表这层没有 KV cache，而是“这层不拥有 compressed cache”；它的 SWA cache 是另一个模块。

1.3 跨层共享怎么工作

  • is_kv_source = layer_id in kv_source_layer_ids。
  • 对每个 compress_ratio>0 的层，kv_source_layer_id = max(s for s in sources if s <= layer_id)。
  • 非 source 层把自己的 compressed_cache_prefix 指向 source 层的前缀（attention.py:605-619）。
  • 运行时 attention 通过 forward_context 拿到 source 层的 cache，而不是自己写一份。

效果：

layer 0,1:   SWA only
layer 2:     SWA + compressed(ratio2) ← source
layer 3-7:   SWA + read layer2's compressed
layer 8:     SWA + compressed(ratio2) ← source
...
layer 20:    SWA + compressed(ratio1) ← source
layer 21-39: SWA + read layer20's compressed

这就是 DeepSeek V4.1 能把 40 层长上下文的 KV 压到“4 层 compressed”的根本原因。

1.4 字节手算

fp8_ds_mla packed record：swa_bytes_per_token = 584（512 维 fp8 + UE8M0 scale/padding）。 compressed record 也是 584 B/state；ratio=2 时每 token 292 B。

项 公式 128k 上下文
SWA（40 层） 40 × 128 × 584 ≈ 2.99 MB / 请求（固定）
compressed ratio2（3 层） 3 × (S/2) × 584 ≈ 114.8 MB
compressed ratio1（1 层） 1 × S × 584 ≈ 76.5 MB
indexer（8 层，128 维，ratio 2/1） 约 8 × (S/2) × 128 ≈ 67 MB（粗算）
compressor state（4 层） 4 × ring 几 MB 量级
合计 约 260 MB / 128k 请求

对比传统 61 层 MLA（DeepSeek-V3）128k 约 8.6 GiB：V4.1 靠“4 层共享 + 压缩 + SWA”把量级降了一个数量级。
注意：这是每请求的 KV；生产环境靠前缀缓存/分页共享进一步摊薄。

1.5 易错点

  1. head_dim=512 不是 576；qk_rope_head_dim=64 是其中一部分（nope=448）。cache 行是 512，不是 576。
  2. compress_ratios 包含 MTP 层，长度 43 不是 40；layer_id < len 才取，MTP 默认 0。
  3. 非 source 层的 get_kv_cache_spec() 返回 None，但 SWA cache 仍然存在。
  4. kv_source_layer_ids 与 index_source_layer_ids 不是一个集合；indexer 有 8 个 source。
  5. is_kv_source 只在 backbone（layer_id < num_hidden_layers）成立；MTP 不算。

2.2 每层 cache

层类型 数量 spec 关键字段 增长
MLA 24 MLAAttentionSpec num_kv_heads=1, head_size=576, max_tp_shards=1 O(S)

MLA 的 head_size 在 vllm/models/kimi_k3/nvidia/mla.py:156：

即使 mla_use_nope=true（不应用 RoPE），代码仍然按 576 分配 cache（qk_rope_head_dim 的槽位保留）。这是读 Kimi 时最容易算错的地方。

KDA 的 spec 在 vllm/models/kimi_k3/nvidia/kda.py:830，最终落到 MambaSpec（vllm/model_executor/layers/mamba/abstract.py:72）：

MambaSpec(
    shapes=tuple(self.get_state_shape()),
    dtypes=...,
    block_size=mamba_block_size,
    mamba_type=...,
    num_speculative_blocks=...,
)

KDA state 形状（mamba_utils.py:305）：

conv_state:      [conv_dim / TP, conv_kernel - 1 + num_spec]
recurrent_state: [num_heads / TP, head_dim, head_dim]
conv_dim = num_heads*head_dim + 2*num_k_heads*head_k_dim

2.3 字节手算（TP=8，FP32 recurrent）

项 公式 量级
MLA KV / token 24 × 576 × 2（bf16） 27,648 B ≈ 27 KiB/token
MLA KV / 128k 131072 × 27648 ≈ 3.4 GiB
KDA / layer / rank conv 36864/8×3×2 + recurrent 96/8×128×128×4 ≈ 0.8 MB
KDA / 69 层 / rank 69 × 0.8 MB ≈ 55 MB（固定）

结论：Kimi 的长上下文成本几乎全在 24 层 MLA；69 层 KDA 的 state 与序列长度无关。
若把 MLA 换成 fp8_ds_mla（656 B/token/layer），24 层约 15.4 KiB/token，128k 约 1.9 GiB。

2.4 易错点

  1. Kimi 的 kda_layers / full_attn_layers 是 1-based：代码用 (layer_idx + 1) in ... 判断；0-based 层号要减 1。
  2. num_key_value_heads=96 是 config 的干扰项；MLA 实际 num_kv_heads=1（latent）。
  3. mla_use_nope=true 不等于 head_size=512；代码仍是 576。
  4. KDA 不是 attention，没有 block table；MambaSpec 的 block_size 是 state block，不是 token block。
  5. KDA state 是 TP 分片的；估算总显存要乘 TP（或按每 rank 算）。

  7. DSV4.1 的非 source 层 get_kv_cache_spec() 返回 None，它的 SWA cache 是谁分配的？
  8. GLM 的 indexer 为什么用 tokens_per_state=4，而不是单独写一个压缩 cache 类？

参考答案

  1. page = 1 head × (32/2) states × 584 = 9,344 B。
  2. 3 × 65536 × 584 + 1 × 131072 × 584 = 114,819,072 + 76,546,048 ≈ 191 MB（约 0.18 GiB）。
  3. 24 × 576 × 2 × 131072 ≈ 3.62 GB ≈ 3.37 GiB。
  4. 11 × 512 × 1 × 131072 ≈ 738 MB ≈ 0.69 GiB。
  5. 12 × 2 × 512 × 2 × 262144 ≈ 6.44 GB ≈ 6.0 GiB。
  6. 因为它是 recurrent state（固定形状的 conv + SSM state），不是按 token 存的 K/V；max_memory_usage_bytes 只看 state 形状和 speculative blocks，不看 max_model_len。
  7. 每层都有一个独立注册的 DeepseekV4SWACache 模块，worker 会把它当作一个 AttentionLayerBase 收集；它的 get_kv_cache_spec() 返回 SlidingWindowMLASpec。
  8. 因为 indexer 的语义就是“每 kpool 个 token 一个 entry”，直接复用 MLAAttentionSpec.tokens_per_state 就能让 vLLM 的 slot mapping/seq_lens/page table 自动按 pool 粒度生成，不需要新 spec 类。

Chapter 02

全链路

spec → group → tensor → bind → slot

从一个模型出发，沿 7 个环节看它的 KV cache 如何从声明走到 kernel。 行号会漂移，用函数名定位。

0. 七步总览

① 层声明 spec         layer.get_kv_cache_spec()
② worker 收集         GPUWorker.get_kv_cache_spec()
③ core 分组           get_kv_cache_groups()
④ core 算显存/布局    get_kv_cache_config_from_groups()
⑤ worker 建 tensor    allocate_kv_cache() → create_kv_cache_views()
⑥ 绑定到层            bind_kv_cache_to_layers() → layer.bind_kv_cache()
⑦ 运行时寻址          BlockTables.compute_slot_mappings() + attention metadata

每一步的输入、输出和关键变量如下。

同一个模型在七步里会以不同形态出现：

步骤 模型侧的对象 这一步之后变成什么
① 层声明 model.layers[i] 里的 attention / linear / indexer / compressor 模块 每条模块返回一个 KVCacheSpec，或 None
② worker 收集 所有 AttentionLayerBase 实例 dict[layer_name, KVCacheSpec]，条目数可能大于层数
③ core 分组 上一步的 dict list[KVCacheGroupSpec]，每个 group 对应一张 block table
④ 算显存 group 列表 bytes_per_block、num_blocks、KVCacheTensor
⑤ 建 tensor KVCacheTensor + spec 每层一个 4D view，指向同一块 int8 backing
⑥ 绑定 4D view + layer 对象 layer.kv_cache
⑦ 运行时 block table + slot mapping kernel 按 slot 读写每层 page

关键是：模型层数不等于 spec 条目数。一层可能注册多个 cache 模块（主 KV + indexer + ring），也可能一个都不拥有（consumer / KV-sharing）。

1.1 一层为什么会有多条 spec

以 Qwen3.8 的一个 full attention 层为例（层号 3、7、…、47）：

model.layers.3.self_attn          → FullAttentionSpec（GQA 主 KV）
model.layers.3.self_attn.qsa      → MLAAttentionSpec（QSA compressed key）
model.layers.3.self_attn.qsa_ring → CircularBufferSpec（未满 group 的 ring）

这三条记录的 layer name 前缀相同，但 key 不同，所以 kv_cache_spec 里是三条 spec，而不是一条。后面的分组会把它们拆到三个 group：主 KV 按 token 增长，QSA compressed 按 4 个 token 一个 state，ring 则每请求固定 1 block。

DeepSeek V4.1 的 source 层 2 更典型：

model.layers.2.self_attn           → MLAAttentionSpec（compressed，ratio 2）
model.layers.2.self_attn.swa_cache → SlidingWindowMLASpec（窗口 128）
model.layers.2.self_attn.indexer   → MLAAttentionSpec（indexer，head 128）
model.layers.2.self_attn.compressor→ CircularBufferSpec（压缩器 ring）

同一层贡献 4 条 spec。非 source 层只贡献 SWA 一条，self_attn 本身返回 None。Kimi 的 MLA 层贡献 MLAAttentionSpec，KDA 层贡献 MambaSpec；GLM 的 sparse MLA 层额外贡献 indexer kpool 与 tail ring。

    kv_cache_spec = {}
    attn_layers = get_layers_from_vllm_config(vllm_config, AttentionLayerBase)
    for layer_name, attn_module in attn_layers.items():

4.1 bytes_per_block

_get_kv_cache_bytes_per_block()（:574）：

bytes_per_block = max(
    sum(spec.page_size_bytes for layer in group.layer_names)
    for group in kv_cache_groups
)

理解：

  • 一个 block id 在每个 group 里都对应一段物理空间；
  • group 内的所有层共享这个 block id，但每层都有自己的 page；
  • 所以 group 的 block 字节 = 该 group 所有 layer 的 page 之和；
  • 取所有 group 的最大值，保证每个 block id 都有足够空间。

C = spec.state_content_size_bytes

然后 .view(dtype) 把字节维变成元素维（例如 C=1024 bytes → 512 个 bf16）。

为什么要 kernel_block_size：manager block 可能是 128，但后端 kernel 只支持 64；blocks_per_page=2，视图第 0 维变成 num_blocks*2，map_kv_caches_to_kernel_blocks() 再把 manager 粒度映射成 kernel 粒度。

关键变量：

  • kernel_block_size：由 prepare_kernel_block_sizes() 选（见 ⑥）；
  • num_layers：这个 KVCacheTensor 包含的层数；
  • layer_stride/block_stride：决定 as_strided 的物理布局；
  • dtype：spec.dtype，决定最后 .view()。

⑥ 绑定到层：bind_kv_cache_to_layers()

    forward_context[layer_name].bind_kv_cache(kv_cache)

每个层的 bind_kv_cache 自己决定怎么解释这个 4D view：

  • MLA（Kimi/GLM/DeepSeek）：[B, H=1, N, C] → [B, N, C]（squeeze H）。
  • Mamba/KDA：把一块 tensor 拆成 conv state / recurrent state（可能多个 view）。
  • GLM indexer：[B, N, H, C] 或 squeeze。
  • Qwen QSA：transpose(1,2) 后 split key/value。

这就是“同一块物理显存，不同层有不同逻辑视图”的地方。

11. 一个具体例子：Qwen3MoE 30B，5 个 token

以 qwen3_moe_inference_flow.md 的输入为例：

序列 0："你好"   → [14, 26]       positions [0, 1]
序列 1："你是谁" → [14, 37, 52]   positions [0, 1, 2]

展平：tokens [14, 26, 14, 37, 52]

Qwen3MoE 30B 的 attention 配置：

48 层，每层都是 full attention（sliding_window=null）
hidden_size = 2048
32 个 Q heads，4 个 KV heads（GQA）
head_dim = 128
dtype = bfloat16

11.1 cache 里存的是什么

对每一层，k_proj / v_proj 把 5 个 token 的 hidden [5, 2048] 投影成：

K = [5, 512] → reshape [5, 4, 128]
V = [5, 512] → reshape [5, 4, 128]

K 还会做 k_norm + RoPE；V 不做 RoPE。cache 只存这两个结果：

  • 不存 hidden state [5, 2048]；
  • 不存 Q [5, 32, 128]；
  • 不存 attention 输出 [5, 2048]；
  • 不存 MoE 的专家输出；
  • 不存权重矩阵本身。

每个 token、每个 KV head、每个 head_dim 的 K 和 V 都进 cache。32 个 Q heads 不单独存，它们共享 4 个 KV heads。

11.2 放到什么 tensor

所有 48 层的 FullAttentionSpec 完全相同，所以只有 1 个 group：

KVCacheGroupSpec(
    layer_names=[48 层],
    kv_cache_spec=FullAttentionSpec(
        block_size=16,          # 假设默认 block_size=16
        num_kv_heads=4,
        head_size=128,
        head_size_v=128,
        dtype=bfloat16,
    ),
)

每层的逻辑 view 是：

[num_blocks, 4, 16, 256]   # bf16 元素
       B      H   N    C
  • B 是 num_blocks，不是 batch=2；
  • H=4 是 KV heads；
  • N=16 是一个 block 的 token 槽位；
  • C=256 个 bf16 元素 = 512 B，其中 K 128 个元素、V 128 个元素。

逻辑上 [B,H,N,C]，物理 stride 由 KVCacheLayout 决定；kernel 可以把最后维拆成 K view 和 V view，但底层是同一页。

每层一个 page 的字节数：

4 heads × 16 tokens × (128 + 128) × 2 B = 32 KiB

48 层共享一个 KVCacheTensor 描述符：

bytes_per_block = 48 × 32 KiB = 1.5 MiB

实际显存仍然只有一块 int8 backing；KVCacheTensor 只是描述 48 层的 offset / layer_stride / block_stride。

11.3 block table 和 slot

假设两个序列各分到 1 个 block（block_size=16）：

seq 0: block_table = [7]
seq 1: block_table = [8]

展平后的 5 个 token 对应：

slot = block_table[req][pos // 16] * 16 + (pos % 16)

token 14 (seq0, pos0) → 7*16+0 = 112
token 26 (seq0, pos1) → 7*16+1 = 113
token 14 (seq1, pos0) → 8*16+0 = 128
token 37 (seq1, pos1) → 8*16+1 = 129
token 52 (seq1, pos2) → 8*16+2 = 130

slot_mapping = [112, 113, 128, 129, 130]。

每个 slot 在每层 page 里对应一个 K/V 位置；48 层各写一份。5 个 token 的实际 K/V 数据量：

5 × 4 heads × 128 × 2 (K,V) × 2 B × 48 layers = 480 KiB

但物理上按 block 分配了 2 个 block：

2 × 1.5 MiB = 3 MiB

其中大部分 slot 暂时没有 token；这是 paged KV 的块粒度开销，不是 cache 存了 3 MiB 的有效 K/V。

分组与后端

为什么 group 跨层、backend 怎么选

分组与后端解决两个问题：

  1. 为什么同一个模型会有 2–6 个 KV cache group？
  2. 每个 group 用哪个 attention backend、block table 怎么建？

0. 一句话

group 的边界 = “是否共享同一张 block table”。
同 group 的层共享 block id 序列和分配/回收；不同 group 可以有不同 block_size、page_size、max_num_blocks_per_req、甚至不同 backend。

1. 分组算法：get_kv_cache_groups()

vllm/v1/core/kv_cache_planning.py:1113，决策顺序：

disable_hybrid_kv_cache_manager?
  └─ 是：把所有 spec 强行统一成 full attention 风格（只用于兼容）
attention-free?
  └─ 是：返回 []
hisparse?
  └─ 是：HiSparse 自己的分组
所有层 spec 可 merge?
  └─ 是：1 个 group（最常见：纯 full attention 模型）
所有层是同一“类型”?
  └─ 是：1 个 UniformTypeKVCacheSpecs group
否则：
  ├─ 尝试 packed groups（block-outermost）
  ├─ 尝试统一 page size，按 page size 分组
  ├─ 失败则 full-allocation fallback
  └─ hidden-state 层单独 group

1.1 什么叫“可 merge”

KVCacheSpec.merge(specs) 要求所有字段兼容。例如 MLAAttentionSpec.merge 要求：

  • block_size 相同；
  • num_kv_heads、head_size、head_size_v 相同；
  • dtype、tokens_per_state、kv_quant_mode 相同；
  • cache_dtype_str、model_version、alignment 相同。

DeepSeek V4.1 的 SWA 和 compressed 显然不满足（窗口 vs 全量、head 512 vs 512 但 tokens_per_state 不同），所以不同 group。

1.2 什么叫“同一类型，但 head size 不同”

UniformTypeKVCacheSpecs.from_specs()（kv_cache_interface.py:1235）允许：

  • 同一个大类（都是 FullAttentionSpec / 都是 SlidingWindowSpec / 都是 MambaSpec）；
  • block_size、dcp_sharded 相同；
  • is_uniform_with_collection() 为真（同类型，token slot 数一致）。

这时所有层放一个 group，page_size_bytes 是各层 page 之和，max_memory_usage_bytes 取最大 page 数。

例子：纯 full attention 模型里，有些层 head_size 不同但都是 full attention；或者 Qwen 的 12 层 full attention 完全同构，直接 merge 成一个 group。

1.3 混合类型：按 page size 分组

_get_kv_cache_groups_uniform_page_size()（:416）的假设：

  1. 每个 block 的物理字节在 group 间必须相同（否则碎片/分配复杂）；
  2. block_size 当前用全局 cache_config.block_size；
  3. 每 token 每层字节、每组层数尽量相同；
  4. 同 group 内 attention 类型一致。

它先按 layer_spec 分桶，再尝试 merge；然后按 page size 拼成 group。
这就是为什么四个模型会拆成多个 group，而不是“一层一个 group”。

3. 为什么 group 内要共享 block table

KVCacheManager 对每个 group 建一个 SingleTypeKVCacheManager（vllm/v1/core/single_type_kv_cache_manager.py）：

  • 维护该 group 的 block_table；
  • 负责 allocate_slots / free / 前缀命中；
  • 每个 group 的 block_size、max_num_blocks_per_req 可以不同。

模型 runner 的 BlockTables（vllm/v1/worker/gpu/block_table.py:17）为每个 group 保存：

  • block_sizes[group]；
  • max_num_blocks_per_group[group]；
  • block_table_ptrs[group]；
  • slot_mappings[group]。

forward 时，同一 group 的所有层用同一张 block table；不同 group 的层用各自的表。

好处：

  • 一个 group 的压缩/窗口策略可以独立演进；
  • 不同 group 可以有不同的 block size（DSV4 SWA=32 vs compressed=64/128）；
  • 线性注意力 state 不需要按 token 分配，单独 group 管理。

代价：

  • 多 group 的前缀命中要协调（HybridKVCacheCoordinator，kv_cache_coordinator.py:609）；
  • 每个 group 都要满足 block_size % hash_block_size == 0（不可前缀缓存的 ring 除外，见 kv_cache_coordinator.py:650-666）。

3.1 group 不是“每组单独分配一块显存”

get_kv_cache_config_from_groups() 先算：

bytes_per_block = max over groups( sum(page_size for layer in group) )
num_blocks      = available_kv_bytes // bytes_per_block
size            = bytes_per_block * num_blocks

然后为每个 group 生成一个 KVCacheTensor（UniformTypeKVCacheSpecs 内部如果 page 不同，会拆成多个 tensor）：

KVCacheTensor(
    size=size,                 # 所有 tensor 的 size 相同
    layers=[...],              # 这个 group 里的层
    layer_stride=...,          # 相邻 layer 的 page 间隔
    block_stride=...,          # 相邻 block 的间隔
    offset=...,                # 在这块 backing 里的起点
)

真正分配显存只有一次（allocate_kv_cache()）：

assert len({t.size for t in kv_cache_tensors}) == 1
buf = torch.zeros(size, dtype=torch.int8, device=device)
for tensor in kv_cache_tensors:
    views = create_kv_cache_views(buf, spec, ..., tensor)
    kv_caches.update(zip(tensor.layers, views))

所以准确的层级是：

对象 数量 说明
backing buffer 1 一块 int8 显存，所有 group 共享
KVCacheTensor 每个 group 1 个（UniformType 可能多个） 描述 offset / layer_stride / block_stride，不是独立显存
layer view 每个 spec 条目 1 个 每层拿到的 4D [B,H,N,C] 视图
block table 每个 group 1 张 group 内所有层共用

KVCacheTensor 的注释写得很直接：地址范围重叠的 tensor alias 同一段字节；不同 group 的 tensor 从同一个 backing 的 byte 0 开始叠放，因为一个 block id 在任一时刻只属于一个 group。

3.2 每层一个 tensor 行不行？

分两层看：

  • view 层：可以，而且现在就是每层一个 view（layer.kv_cache 是 4D tensor）。同 group 的层页大小相同，用 layer_stride 串起来即可。
  • 物理分配层：没必要。每层单独 torch.zeros 会变成几十次分配，带来对齐/碎片开销，而且 block id 仍然是按 group 分配的，单独分配并不会让寻址更简单。

真正不能做的是“每层一张 block table”。因为：

  1. 一个 block id 要同时代表该 group 内所有层的 page；分开后同一个逻辑 token block 在每层会有不同 block id，scheduler/前缀缓存要维护 N 套映射。
  2. 不同 spec 的 block 语义不同：Mamba state 不随 token 增长，ring 每请求只有 1 block，SWA 有窗口；它们无法和 paged KV 共用一张 block table。
  3. attention metadata 按 group 构建；kernel 一次拿一张 group block table，不会为每层各拿一张。

所以 group 的本质不是“给每层分配 tensor”，而是把可以共享同一张 block table 的层放在一起，作为一个分配/回收单元。tensor 只是这个单元在显存里的布局描述。

  • 返回 int：必须是精确值；
  • 返回 MultipleOf(n)：接受 n 的倍数。

select_common_block_size()（vllm/v1/worker/utils.py 内）选一个所有 backend 都支持、且能整除 manager block size 的最大值。

例子：

  • DSV4.1 SWA backend：[MultipleOf(32)]，preferred 256；
  • GLM indexer：32/64（SM120 只支持 64）；
  • 普通 FlashAttention：通常 128/256。

4.4 为什么 kernel_block_size 会小于 block_size

manager 用 128 token 一个 block，但某个 kernel 只支持 64；create_kv_cache_views 把视图第 0 维拆成 num_blocks*2，map_kv_caches_to_kernel_blocks() 再按 manager block 分组。
这就是你在 tensor shape 里看到 B*2 的原因。

5. block table 与 slot mapping

5.0 block、page、slot、block table 到底分别是什么

先把四个词分开：

概念 是什么 不是什么
block 一条序列的 16 个 token 位置（block_size=16）的分配单位 不是 16 个 hidden state，也不是 16 个 token 的全局集合
page 某一层在一个 block 里的 K/V 存储区 不是整层的 cache，也不是整个模型的 cache
block id 物理 block 的编号，例如 7、8 不是 token id，也不是层号
block table 每条请求的“逻辑 block 序号 → 物理 block id”映射 不是 K/V 数据本身
slot 一个 token 在物理 page 里的具体位置 不是 token 在序列里的位置；它是物理地址的一部分

block_size=16 的准确含义是：

一条序列最多把 16 个连续 token 放进一个 block；需要第 17 个 token 时，再分配下一个 block。

block id 是每层 view 的第一维下标

每层拿到的 cache view 是：

layer.kv_cache: [num_blocks, H, N, C]
                       ^
                     block id

block id = 7 就是第 7 号物理 block 在这个 view 第一维的下标：

layer0.kv_cache[7]   # layer 0 的 block 7 对应的 page
layer1.kv_cache[7]   # layer 1 的 block 7 对应的 page
...
layer47.kv_cache[7]  # layer 47 的 block 7 对应的 page

它们是不同的物理 page，只是共用同一个 block id。物理地址由 layer_stride 和 block_stride 算出来。

block id 由 BlockPool 分配，是一个 0..num_blocks-1 的整数句柄，不是字节地址，也不是 token id。

block_table = [7] 的意思是：

这条请求的逻辑 block 0  →  物理 block 7

它只描述“请求的逻辑块到物理块的映射”，不包含 token，也不包含 K/V。真实 buffer 里每行有 max_num_blocks_per_req 个位置；只有前面的有效项有值，后面不用。

例如 Qwen3MoE 30B，48 层、4 个 KV heads、head_dim=128、bf16：

一个 block id = 7
  layer 0 的 page 7：16 个 token 槽位 × 4 heads × 128 维 K/V
  layer 1 的 page 7：16 个 token 槽位 × 4 heads × 128 维 K/V
  ...
  layer 47 的 page 7：16 个 token 槽位 × 4 heads × 128 维 K/V

同一个 block id 7 在每一层都有一页，但页的物理地址不同：

layer l, block 7 的起始字节 =
    tensor.offset + l * layer_stride + 7 * block_stride

所以“block 7”不是一块连续的 1.5 MiB；它是 48 个 page 的逻辑集合，每层一页。KVCacheTensor 的 layer_stride / block_stride 就是用来算这些地址的。

一个 block 里到底存了多少 token

  • 容量：最多 16 个 token；
  • 实际：如果序列只有 2 个 token，这个 block 只写了 2 个 slot，另外 14 个 slot 空着；
  • 空 slot 仍然占着物理 page 的空间，这是 block 粒度的内部碎片。

上一个例子里：

seq0 "你好"   → block 7，只用了 slot 0、1
seq1 "你是谁" → block 8，只用了 slot 0、1、2

两个序列各自有自己的 block table：

seq0: [7]
seq1: [8]

如果 seq1 继续生成到 20 个 token：

token 0..15  → block 8  （逻辑 block 0）
token 16..19 → block 9  （逻辑 block 1，新分配）

seq1 的 block_table = [8, 9]

第 16 个 token 的 slot：

block_table[1][16 // 16] = 9
slot = 9 * 16 + (16 % 16) = 144

block table 的 tensor 形状

BlockTables 为每个 group 维护：

block_table: [max_num_reqs, max_num_blocks_per_req]  # int32

每一行是一条请求；行里的第 k 个元素是逻辑 block k 对应的物理 block id。序列长度不够时，后面的槽位不用。

block 的元数据在 BlockPool 里

KVCacheBlock 只存管理信息：

block_id、ref_cnt、block_hash、is_null ...

K/V 数据不在 KVCacheBlock 里，而在 KVCacheTensor 的 page 里。BlockPool 负责分配/回收 block id，并维护引用计数。

前缀缓存时 block 会共享

如果两条请求的前缀完全相同，某个完整 block 的 hash 相同，BlockPool 会让两条请求的 block table 指向同一个物理 block id，并增加 ref_cnt：

seq0 block_table = [7, 9]
seq1 block_table = [7, 11]   # 第一个 block 共享 7

共享的是 block id 和它对应的所有层 page；不是把 K/V 复制一份。部分填充的 block 不能共享，因为 hash 只对完整 block 稳定。

5 层玩具模型的一次 forward

为了看清结构，把模型缩成 5 层、2 个 KV heads、head_dim=2、bf16、block_size=16。输入：

"你好" → tokens [14, 26]，positions [0, 1]

第 0 步：分配 block

BlockPool 从空闲块里分配一个物理 block，假设是 7：

KVCacheBlock(block_id=7, ref_cnt=1)

block_table[req] = [7]      # 逻辑 block 0 → 物理 block 7
slot_mapping     = [112, 113]  # 7*16+0, 7*16+1

这 5 层属于同一个 group，所以只有一张 block table；5 层都用 block id 7。

第 1 步：layer 0 forward

H0 = [2, hidden]
K0 = H0 @ Wk0 → [2, 2, 2]    # token, KV head, head_dim
V0 = H0 @ Wv0 → [2, 2, 2]
Q0 = H0 @ Wq0 → [2, Q head, 2]   # 不存

写入 layer 0 的 page：

layer0.kv_cache[7]   # 逻辑形状 [2 heads, 16 slots, 4]（K 2 + V 2）

slot 0: K0[0], V0[0]   # token 14
slot 1: K0[1], V0[1]   # token 26
slot 2..15: 空

layer 0 的 attention 读自己的 page 7：token 26 看 slot 0/1，token 14 看 slot 0。

第 2 步：layer 1 forward

layer 0 的输出进入 layer 1：

K1 = H1 @ Wk1 → [2, 2, 2]
V1 = H1 @ Wv1 → [2, 2, 2]

写入 layer 1 自己的 page 7：

layer1.kv_cache[7]

slot 0: K1[0], V1[0]
slot 1: K1[1], V1[1]

layer 0 的 page 7 不会被覆盖；layer 1 的 page 7 是另一段地址。

第 3 步：layer 2..4

重复同样的事。每层都写自己的 page 7，slot 0/1 分别对应 token 14/26。

第 4 步：forward 结束后

block_table = [7]
slot_mapping = [112, 113]

block 7:
  layer0 page7: slot0=K/V(14), slot1=K/V(26)
  layer1 page7: slot0=K/V(14), slot1=K/V(26)
  layer2 page7: slot0=K/V(14), slot1=K/V(26)
  layer3 page7: slot0=K/V(14), slot1=K/V(26)
  layer4 page7: slot0=K/V(14), slot1=K/V(26)

所以：

  • block_table=[7] 只有 1 个 entry，表示逻辑块 0 → 物理块 7；
  • block 7 本身不是“一个 page”，而是 5 个 layer page 的逻辑集合；
  • 每层 page 7 的物理地址不同，但都用同一个 block id 寻址；
  • 2 个 token 只用了 slot 0、1，slot 2..15 空着。

第 5 步：再 decode 一个 token

新 token 在 pos 2，仍然在同一个 block：

slot = 7*16 + 2 = 114
block_table 仍然是 [7]

每层在 page 7 的 slot 2 追加自己的 K/V。

如果继续到第 17 个 token（pos 16），需要新 block 8：

block_table = [7, 8]
slot(16) = 8*16 + 0 = 128

这时 5 层各有 page 7 和 page 8 两页。

为什么逻辑 block 是 0

“逻辑 block”是序列内部的编号，不是物理编号：

logical_block = position // block_size

所以：

pos 0..15  → logical block 0
pos 16..31 → logical block 1

任何请求都从 position=0 开始，因此任何请求都有自己的逻辑 block 0。它是 block table 的行内下标：

block_table[req][0] = 这条请求第 1 个逻辑块用的物理 block id

两条不同的请求可以都有逻辑 block 0：

seq0 logical block 0 → physical block 7
seq1 logical block 0 → physical block 8

逻辑编号相同，物理编号不同，这正是 block table 存在的意义：把稳定的“序列内第几块”映射到实际分配的“物理第几块”。

“5 层共用一张 block table”怎么理解

共用的只是索引表，不是 K/V 数据。

                 block_table[req]
                       [7]
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
 layer0.kv_cache[7]  layer1.kv_cache[7] ... layer4.kv_cache[7]
       page A             page B             page E
  • block table 里只有整数 7，没有 K/V；
  • 5 层都读同一个 entry 7；
  • 每层用自己的 view 取第 7 行，得到自己的 page；
  • page A/B/E 是不同物理地址，K/V 内容也不共享。

所以“共用 block table”= 共用同一套“逻辑块 → 物理块”的编号；不是共用同一页，也不是共用 K/V。

一个 block 多大，什么时候分配

大小：一个 block id 的大小不是一个 page，而是 group 内所有 layer 的 page 之和：

page_size(layer) = num_kv_heads × block_size × (head_size + head_size_v)
                   × dtype_bytes / tokens_per_state

bytes_per_block  = sum(page_size(layer) for layer in group)

5 层玩具模型（H=2, D=2, block=16, bf16）：

page_size = 2 × 16 × (2 + 2) × 2 = 256 B
bytes_per_block = 5 × 256 = 1280 B

真实 Qwen3MoE 30B（48 层，H=4, D=128, block=16, bf16）：

page_size = 4 × 16 × (128 + 128) × 2 = 32 KiB
bytes_per_block = 48 × 32 KiB = 1.5 MiB

什么时候分配：分两个阶段，不要混：

  1. 启动时分配物理显存
    get_kv_cache_config_from_groups() 用可用显存算 num_blocks 和 size = bytes_per_block × num_blocks；allocate_kv_cache() 一次性 torch.zeros(size, int8) 分配整块 backing。所有 block 的物理空间在这一刻就有了，BlockPool 把它们加入空闲链表。

  2. 请求到来时分配 block id
    prefill 调度时，allocate_slots() 按 ceil(tokens / block_size) 计算需要几个逻辑 block，从 BlockPool 取空闲 block id，写进该请求的 block_table，并把 ref_cnt 加 1。这时才决定“逻辑 block 0 → 物理 block 7”。

所以“你好”两个 token：

启动时：物理显存里已经有 num_blocks 个 block 的空间
请求时：BlockPool 分配 block id 7
prefill：K/V 写进 block 7 的每层 page

block 7 的物理空间不是请求时临时 malloc 的；请求时只是把一个已有 block id 映射给这条请求。decode 超过 16 个 token 时，再分配下一个 block id（例如 8），追加到 block table。

写 page 的真实 tensor 操作

layer0 page7 slot0 ← K/V(14) 不是 PyTorch 的 tensor[slot] = kv，而是调用 CUDA 的 scatter kernel：

# vllm/v1/attention/backends/flash_attn.py
def do_kv_cache_update(self, layer, key, value, kv_cache, slot_mapping):
    # kv_cache: [num_blocks, H, N, 2*D]
    # transpose -> [num_blocks, N, H, 2*D]
    key_cache, value_cache = kv_cache.transpose(1, 2).split(
        self.head_size, dim=-1
    )
    reshape_and_cache_flash(
        key, value,
        key_cache, value_cache,
        slot_mapping,
        self.kv_cache_dtype,
        layer._k_scale,
        layer._v_scale,
    )

key_cache / value_cache 是 [num_blocks, block_size, H, D] 的 view。reshape_and_cache_flash 的 CUDA kernel 按 token 做：

slot_idx = slot_mapping[token_idx];
block_idx = slot_idx / block_size;
block_offset = slot_idx % block_size;

key_dst = key_cache
        + block_idx * block_stride
        + block_offset * page_stride;

copy(key[token_idx], key_dst, num_heads * head_size);
copy(value[token_idx], value_dst, num_heads * head_size);

对 token 14（slot 112，block_size=16）：

block_idx = 112 / 16 = 7
block_offset = 112 % 16 = 0

key_cache[7, 0, :, :] = key[0]
value_cache[7, 0, :, :] = value[0]

对 token 26（slot 113）：

key_cache[7, 1, :, :] = key[1]
  • 这是真正的显存写；目标地址已经在启动时分配好；
  • slot_mapping 是 [num_tokens]，kernel 忽略 -1 的 padding token；
  • 5 层各调用一次同样的 kernel，只是 kv_cache view 不同；
  • Qwen3 在写之前已经做完 k_norm 和 RoPE，所以写进去的是投影 + norm + RoPE 后的 K；V 是投影后的 V。

多 group 的玩具例子

模型只有 3 层，但有两组：

layer 0, 1：full attention
  H = 2, D = 2, block_size = 16, bf16
  page_size = 2 × 16 × (2+2) × 2 = 256 B

layer 2：sliding-window attention
  H = 1, D = 2, block_size = 8, bf16
  page_size = 1 × 8 × (2+2) × 2 = 64 B

分组：

G0 = [layer0, layer1]   FullAttentionSpec, block_size 16
G1 = [layer2]           SlidingWindowMLASpec, block_size 8

bytes_per_block = max(2×256, 64) = 512 B。假设 num_blocks = 4，backing 一共 2048 B。

输入仍然是：

"你好" → tokens [14, 26]，positions [0, 1]

分配两个物理 block（同一个 BlockPool，id 全局唯一）：

G0 拿到 block 2
G1 拿到 block 1

两张 block table：

G0 block_table[req] = [2]   # 逻辑 block 0 → 物理 2
G1 block_table[req] = [1]   # 逻辑 block 0 → 物理 1

两张 slot mapping：

G0: slot(0) = 2*16 + 0 = 32
    slot(1) = 2*16 + 1 = 33
    slot_mapping = [32, 33]

G1: slot(0) = 1*8 + 0 = 8
    slot(1) = 1*8 + 1 = 9
    slot_mapping = [8, 9]

写入：

layer0 page2 slot0/1 ← K/V(14), K/V(26)   # G0
layer1 page2 slot0/1 ← K/V(14), K/V(26)   # G0
layer2 page1 slot0/1 ← K/V(14), K/V(26)   # G1

注意：

  • 同一个请求有两张 block table，不是一张；
  • layer0/1 用 G0 的表，layer2 用 G1 的表；
  • 同一个 token 14 在两个 group 的 slot 不同：G0 是 32，G1 是 8；
  • 因为 G0 的 block_size=16、G1 的 block_size=8，所以“逻辑 block 0”覆盖的 token 范围也不同。

如果序列有 10 个 token：

G0: token 0..15 都在逻辑 block 0 → block_table [2]，只需 1 个 block
G1: token 0..7  在逻辑 block 0 → 物理 1
    token 8..15 在逻辑 block 1 → 物理 3

G1 block_table = [1, 3]

同一个 pos=8 的 token：

G0 slot = 2*16 + 8 = 40
G1 slot = 3*8 + 0 = 24

所以 slot 必须按“group 自己的 block_size”算，不能拿一个全局公式套所有 group。

这个 max 会浪费空间吗

会。上面的例子里：

G0 block = 512 B
G1 block = 64 B
bytes_per_block = 512 B

当 G1 拿到一个 block 时，它只用 64 B，剩下 448 B 在这个 block 槽位内部空着。这是 block 级内部碎片，确实浪费。

为什么不能让 G1 的 block 只占 64 B？因为 block id 是全局共享的：

block 1 今天可能属于 G1，明天释放后可能分配给 G0

如果 G1 的 block 1 只从 byte 64 开始，而 G0 的 block 0 占 0..512，两者会重叠。为了保证任意 block id 在任意时刻都能被任意 group 使用，每个 block 槽位都必须按最大的 group 留足空间：

block slot 大小 = max over groups(bytes_per_block)

这是用“少量内部碎片”换：

  • 一套全局 block id；
  • 一套共享 BlockPool；
  • 简单的按 block 寻址；
  • 不需要为每个 group 维护独立的地址空间。

代价是：如果某个 group 的 page 远小于最大 group，它持有的 block 尾部会浪费。实际模型的 group page 差距通常没有玩具例子这么夸张；但如果一个小 page group 占满所有 block，浪费就会很明显。这是统一 block id 空间的设计取舍，不是没有代价。

5.1 block table 是 per-group 的

BlockTables 构造（vllm/v1/worker/gpu/model_runner.py:709）时传入：

block_sizes=[group.spec.block_size ...]
max_num_blocks_per_group=[...]
slot_mapping_enabled=[group.spec.uses_slot_mapping ...]
dcp_sharded=[...]

每个 group 一行 max_num_blocks_per_group，存物理 block id。

5.2 slot mapping 是 per-token 的

compute_slot_mappings()（block_table.py:194）为每个可写 token 算：

slot = block_table[req, pos // B] * B + (pos % B)

CircularBufferSpec.uses_slot_mapping=False，所以 ring 不生成 slot；层自己按 pos % ring 寻址。

5.3 group 与 layer 的映射

build_slot_mappings_by_layer()（attn_utils.py:448）把 group 的 slot mapping 分发给 group 内每个 layer：

for slot_mapping, kv_cache_group in zip(slot_mappings, kv_cache_groups):
    for layer_name in kv_cache_group.layer_names:
        slot_mappings_by_layer[layer_name] = slot_mapping

forward 时 forward_context.slot_mapping[layer_name] 就是它。

7. 易错点

  1. group 不是按“层类型”简单分的，而是按 spec merge / page size；同是 MLA，ratio 不同就会分 group。
  2. UniformTypeKVCacheSpecs 不是“所有层一样”；它允许 head size 不同，只要 token slot 数一致。
  3. 同一 group 内不同 backend 会被拆成多个 AttentionGroup，但仍是同一 KV group（同一 block table）。
  4. block_size 可以 group 间不同；不要假设全局只有一个。
  5. CircularBufferSpec 不参与前缀缓存，也不生成 slot mapping；它每请求固定 1 block。
  6. MambaSpec 的 block_size 不是 token block；它的 page 是 state，max_memory_usage_bytes 与 max_model_len 无关。

Chapter 04

一次请求全流程

“你好，你是谁”的 6 个 token 从 prefill 到 decode

目标：把“临时 tensor、cache tensor、每层是否复用、为什么 group 跨层”一次讲透。 为了讲形状，假设 tokenizer 把“你好，你是谁”切成 T=6 个 token；实际可能是 4–8 个，形状只跟 T 有关。

0. 先纠正三个误解

  1. KV cache 不是“一份所有层共用”的 K/V。
    每一层都有自己的 K/V（或 MLA latent），内容不同；共享的是block id / block table / slot_mapping 这些元数据。
  2. KV cache 里存的不是 token id，也不是 hidden state。
    存的是每层、每个 token 的 K 和 V 向量（MLA 存 latent+rope）。token id 只在 input_ids 里，是一次性的。
  3. block id 不是物理地址。
    block_table[req][block_idx] = 42 表示“第 2 个逻辑页映射到物理页 42”；层 l 的页 42 还有自己的 layer_stride 偏移。

1. 一句话答案

Prefill 时，每层为这 6 个 token 各算一份 K/V，按同一个 slot_mapping 写进各自的 page；decode 时每层只追加 1 个 slot。所有层共享“页号/槽位”的编号，但不共享 K/V 内容。

2. 时间线：从请求到第一个输出 token

2.1 请求到达（step 0）

输入：“你好，你是谁” → tokenizer → 6 个 token。

张量 shape 内容 生命周期
input_ids [6] 6 个 token id 本步临时
positions [6] [0,1,2,3,4,5] 本步临时
block_table [1, max_blocks] 空 每请求持久（行宽按 max_model_len 预分配）
KV cache 启动时已分配 全 0 持久

此时还没有分配任何 block；slot_mapping 也还不存在。

2.2 Prefill（step 1）

调度器给请求分配 1 个物理 block，假设 block_id=42；block_size=16，所以这个 block 覆盖 16 个 slot：

slot(p) = block_table[p // 16] * 16 + (p % 16)
        = 42 * 16 + p
        = 672 + p
逻辑位置 p 0 1 2 3 4 5
slot 672 673 674 675 676 677

临时张量（每层都会重新算）：

以 GQA（Qwen 风格，Hq=24, Hkv=2, D=256）为例：

张量 shape 内容
hidden_states [6, 2560] 上一层输出（Qwen hidden=2560；第 0 层是 embedding）
q [6, 24, 256] 6 个 token × 24 个 Q 头
k [6, 2, 256] 6 个 token × 2 个 KV 头
v [6, 2, 256] 同上
attn_out [6, 24, 256] 本层 attention 输出
logits [1, vocab] 只取最后一个位置（不要求 prompt logprobs 时）

写入 cache：

slot_mapping = [672, 673, 674, 675, 676, 677]   # [6] int32
reshape_and_cache(k, v, k_cache, v_cache, slot_mapping)

每层的 cache 视图（当前 vLLM 逻辑布局）：

GQA:  [num_blocks, Hkv=2, block_size=16, C=512]   # C 里包含 K 256 + V 256
MLA:  [num_blocks, 1,     block_size=16, C=576]   # 512 latent + 64 rope

对 block_id=42、layer=0，写入的是：

# 当前逻辑视图 [B, H, N, C] 把 K/V 打包在 C 里；
# 某些 kernel 会 split 成两个 [B, H, N, 256] 视图：
k_view[42, :, 0:6, :]  ← k[0:6]
v_view[42, :, 0:6, :]  ← v[0:6]

layer 1 写的是另一块 cache（不同的 layer_stride），但同样使用 block 42 和 slot 672..677。

2.3 采样（step 2，真实 vLLM 中与 prefill 同一个 engine step）

vLLM 的实际执行是 execute_model（prefill forward）→ sample_tokens（lm_head + sampler），两者在同一个 EngineCore.step 内；这里拆成两步只是为了分别看清 KV 和 logits 的 shape。

  • 只取最后一个位置（pos 5）的 hidden state → lm_head → logits [1, vocab]；
  • 采样得到第一个输出 token；
  • 6 个 prompt token 的 KV 全部保留，不释放。

2.4 Decode 一个 token（step 3）

新 token 的 position = 6，slot = 672 + 6 = 678。

张量 shape 内容
input_ids [1] 新 token
positions [1] [6]
slot_mapping [1] [678]
block_table [1, max_blocks] [[42, …]]（没变）
seq_lens [1] [7]
q [1, 24, 256] 只算新 token
k / v [1, 2, 256] 只算新 token

Attention 读 block 42 的 slot 672..678，共 7 个位置；写只写 678。

一句话：decode 每层只新增 1 个 K/V，但 attention 要读历史全部 KV。

4. 每层都复用同一份 KV 吗？

默认不是。 每层有自己的 K/V（不同权重算出来的），不能复用。
“复用”的准确说法是：

对象 同 group 的层是否共享
block id（42） 是
block table 是
slot_mapping 是
seq_lens / num_computed_tokens 是
KV 内容 否（每层独立 page）
KDA/GDN state 否（每层独立 state）

为什么共享 block id 不会串内容？因为每层 page 的物理地址不同：

layer 0 page 42: offset + 0 * layer_stride + 42 * block_stride
layer 1 page 42: offset + 1 * layer_stride + 42 * block_stride

block_table 只存 42；kernel 用 layer_stride 找到“这一层的 42”。

5. 为什么 group 是“跨层”的？

因为 一个 block id 必须同时代表 group 内每一层的一个 page。

调度器分配 block 42 时，不是只给 layer 0 分配，而是给 group 内所有层各分配一页；这样：

  • 一张 block table 就能服务几十层；
  • 分配/回收只需要操作一个 id；
  • 所有层的 slot_mapping 完全一致（同一批 token 在同一位置）；
  • bytes_per_block = sum(page_size for layer in group)，一次算清。

如果每层独立分配，就会有 L 张 block table、L 套碎片和 L 次调度，复杂度爆炸。
所以 vLLM 按“生命周期/形状相同”把层分组：

  • 全 attention 层 → 一个 group；
  • SWA 层 → 另一个 group（窗口不同，页的生命周期不同）；
  • KDA/GDN → 另一个 group（state 不按 token 增长）；
  • compressed/indexer/ring → 各自 group。

group 跨层，是为了“元数据共享 + 一次分配”，不是为了“内容共享”。

6. 真正的跨层内容共享：DeepSeek V4.1

普通 GQA/MLA 不共享内容。但 DeepSeek V4.1 是例外：

  • 只有 kv_source_layer_ids=[2,8,14,20] 拥有 compressed KV；
  • layer 3–7 通过 compressed_cache_prefix 读 layer 2 的 cache；
  • 这些 consumer 层不写自己的 compressed cache（get_kv_cache_spec() 返回 None）。

所以 V4.1 的 “group” 里既有“每层独立 SWA”，也有“source 层共享 compressed”。
读代码时看到 is_kv_source / compressed_cache_prefix，就知道这是模型级共享，不是通用 group 行为。
